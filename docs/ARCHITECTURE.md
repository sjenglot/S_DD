# Architecture and safety decision

## Chosen path

A gzip stream can be decoded sequentially but cannot provide the random reads and writes needed by `ntfsresize`. Sparse and copy-on-write layers can save *allocated* bytes in favorable cases but cannot guarantee enough space for an arbitrary compressed raw image. `ntfsclone` works on NTFS partitions, but finding and extracting an arbitrary partition from a gzip stream still requires staged access, and shrinking boot-critical whole-disk layout remains a separate problem. V1 therefore uses explicit scratch storage. The scratch minimum is the full original size plus the fitted image size plus 5% or 2 GiB, whichever is larger. This is conservative for the two simultaneously present files, though other users of scratch can still exhaust it.

The implementation parses MBR and NTFS boot fields without modifying the source. Gzip inspection reads to EOF so its CRC and length are checked, and SDD compares its SHA-256 to the staged stream. A raw source is inspected with bounded reads and file size; SDD checks its file identity and modification times around staging. At restore time the source is staged, then `ntfsresize --check` and `--info` run through a read-only loop partition. The reported minimum plus at least 20% or 2 GiB must fit. A read-only `--no-action` shrink precedes the real resize of the *scratch copy*. `virt-resize --shrink --no-expand-content` then changes the output partition table and copies the already-shrunk NTFS without resizing it again. This matters because `ntfsresize` marks the resized volume for a Windows consistency check; another resize before that check fails. SDD verifies that the staged NTFS length fits the target partition allowance and that the fitted copy retains exactly that length. It also compares boot code, disk signature, active flag, partition type/start, NTFS hidden sectors, and NTFS serial across source and fitted image. It reads fitted and destination NTFS metadata through read-only loop devices. After writing, it compares every byte of the fitted image to the actual destination and verifies that its unused tail was cleared.

The explicit `--test-file-target` mode confines source, scratch, and destination to `.sdd-test-sandbox` and refuses root and block-device targets. For that mode, libguestfs `vfs-minimum-size` measures the NTFS minimum, libguestfs `ntfsresize` shrinks the staged image, and read-only `vfs-type` recognizes fitted and destination NTFS. This allows a rootless regular-file integration run without host loop devices. A real CachyOS file-based run passed for both raw and gzip sources, with every fixture file matching its original SHA-256; Ubuntu and physical hardware remain untested. See [IMPLEMENTATION_REPORT.md](../IMPLEMENTATION_REPORT.md).

`virt-resize` copies pre-partition sectors by default. `--align-first never` prevents partition start movement, and `--no-extra-partition` prevents a new partition in spare space. It also rewrites both CHS fields in the MBR partition entry, even when the start LBA stays the same. SDD checks that boot code, disk signature, active flag, partition type and start LBA remain unchanged, then restores the original three start-CHS bytes in the **scratch fitted image**. Exact start-CHS preservation remains a required postcondition. The end CHS is allowed to change because the partition end and sector count change; the new LBA boundary is checked against the fitted image size. SDD also compares all pre-partition bootloader sectors. Legacy BIOS geometry cannot be inferred reliably from an image, so these checks do not prove boot compatibility. The NTFS volume boot record's length metadata changes during the intentional shrink; SDD checks its signature, serial, hidden-sector field and supported sector size, while the backup NTFS boot sector and MFT relocation are delegated to `ntfsresize`. Windows BCD/boot-sector behavior and any startup-repair need require a physical boot test.

## Limits

Only a single primary MBR type `0x07` NTFS partition with 512-byte sectors is accepted. GPT, multiple partitions, EFI, BitLocker, dynamic disks, non-NTFS, dirty NTFS, unknown boot flags, and unknown sector sizes are refused or fail during utility preflight. A type-`0x07` BitLocker partition with an NTFS-like header is unlikely but the `ntfsresize` check is the authoritative refusal. The old partition's trailing unused space is reserved in the sizing calculation. The target image leaves at least 1 GiB of physical disk unpartitioned. The file-only test mode scales this clearance to 8 MiB and its NTFS free-space margin to at least 32 MiB; production sizing is unchanged.

The destination must be a whole disk with model and serial, no mounted descendants, active swap, or device holders. S_DD uses `lsblk -T` and resolves descendant ancestry using `PKNAME`, then checks source and scratch mount ancestry against the destination and rechecks identity immediately before and after the yes/no confirmation. A fitted-image checkpoint is written before confirmation; resume verifies its hash and structure and is bound to the recorded path/model/serial/capacity. These checks are defense in depth; they cannot make a mistaken confirmation harmless. Stable `/dev/disk/by-id` paths are strongly recommended. The program retains scratch files and logs. No destination bytes are written until fitting and fitted-image checks pass.

The byte comparison verifies that the write reached the selected device over the fitted image length. A separate synthetic real-NTFS integration run checked each source file by SHA-256 after restoration, but a production restore does not compare original files semantically. It does not prove BIOS bootability, Windows CHKDSK success, or instrument function. Actual hardware restoration remains pending.
